# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Backend for the İSİM education/exam rating system. Angular frontend lives in a sibling repo (`education-system-frontend`) and talks to this over REST.

## Commands
- `npm run dev` — nodemon on `src/index.ts` (dev server)
- `npm run build` — `tsc` to `dist/`
- `npm start` — `node dist/index.js` (runs the build, not the sources)
- `npm test` — **stub that exits 1. There are zero tests in this repo.** Nothing is covered; never assume a change is verified because it compiles.

## Architecture

Express 4 + Kysely + TypeScript, **Postgres**. Layering is `routes → controllers → usecases → services(.pg.ts) → Kysely query builder`:

- `routes/*.routes.ts` — one file per domain, mounted in `index.ts` under `/api/<domain>`.
- `controllers/*` — parse the request (`RequestParser`), apply **role-based data scoping** (see below), call a usecase, respond via `ResponseHandler`. DI is manual: each controller `new`s up its services in its own constructor — there is no container.
- `usecases/*` — validation (`ValidationUtils`) + orchestration across services. Thin.
- `services/*.pg.ts` — this is where the real logic and all data access live now, on top of `config/pg.ts` (a single Kysely instance, typed via `types/db.ts` generated by `kysely-codegen`).

### Mongo/Mongoose is dead code, not a fallback — do not "fix" it

`src/models/*` (Mongoose schemas) and every `services/*.service.ts` **without** a `.pg` suffix (`stats.service.ts`, `student.service.ts`, `district.service.ts`, `school.service.ts`, `teacher.service.ts`, `studentResult.service.ts`, `examResults.service.ts`, `exam.service.ts`, `booklet.service.ts`, `gradePromotion.service.ts`, `token.service.ts`, `user.service.ts`, `userSettings.service.ts`, `statistics.service.ts`) are leftovers from the Mongo era. `src/index.ts` never opens a Mongo connection and imports none of them — verified: nothing under `services/*.pg.ts` or any controller imports a non-`.pg` service or a model. They still compile (mongoose/mongodb are still `dependencies`) and still get bundled into `dist/`, which is exactly why they're dangerous: a search for "where is teacher scoring computed" will land you in `stats.service.ts` (1866 lines) first, but the live implementation is `stats.service.pg.ts` (1117 lines). If you find a bug by reading the non-`.pg` file, it is not reachable in production — go find the `.pg` equivalent instead. Same story for `utils/stats.utils.ts`, `utils/migrate-ratings.ts` (its route was removed in `stat.routes.ts`) and `utils/profile-summary.util.ts` (live version is `profile-summary.util.pg.ts`, used by `auth.controller.ts`). Don't delete these unprompted either — that's a separate cleanup decision, not something to do as a drive-by.

Shared utils worth knowing before writing anything new: `response-handler.util.ts` (every response goes through `ResponseHandler.success/notFound/internalError`), `request-parser.util.ts` (`parsePagination`/`parseFilterOptions`/`parseSorting`), `filter.util.ts`, `ranking.util.ts`, `academic-year.util.ts`, `memory-cache.util.ts`, `region-scope.util.ts` (`districtIdsOfRegion`, for the `regionRepresenter` role — see scoping below).

### Migrations

`db/schema.sql` is the readable snapshot; `db/migrations/*.sql` are the numbered, applied-in-order source of truth, tracked in the `schema_migrations` table. `db/migrations/apply-pending.sh` applies whatever hasn't run yet, and it runs **automatically on every push to `main`**: `.github/workflows/docker.yml` copies `db/migrations/` to the server and executes the script before the backend container is redeployed. A migration you add and forget to test locally still hits prod on merge. The script `pg_dump`s to `~/rollback/` before each file and stops at the first error (the backend deploy is then skipped, so the old container keeps serving). `db/migrations/README.md` has the mechanics. Read the migration files, not just `schema.sql`: many carry long comments explaining *why* a column/view exists and what Mongo quirk it's reproducing on purpose.

### Entity code system — read this before touching any code field

`utils/entity-codes.const.ts` defines a hierarchy where **child codes arithmetically contain parent codes**:

```
District 3 digits → School 5 → Teacher 7 → Student 10
teacher = floor(student / 1000)     school = floor(student / 100000)
district = floor(student / 10000000)   school = floor(teacher / 100)
```

Consequences that bite:
- `students.code` **is** `NOT NULL UNIQUE` in Postgres (`db/schema.sql`) — the old Mongo dupes were a known gate, not silently tolerated here. ETL from Mongo will fail loudly on any surviving duplicate; that's intentional, not a bug to route around.
- Changing a school or teacher code **now cascades**: `utils/code-cascade.util.ts` (`cascadeSchoolCodeToTeachers`, `cascadeTeacherCodeToStudents`) re-derives every descendant's code inside the same transaction and logs each change in `code_change_logs` (`caused_by_entity_type`/`caused_by_entity_id` link a cascaded row back to the edit that triggered it). Wired into `school.service.pg.ts`/`teacher.service.pg.ts` `update()`. **What's still missing:** changing a *district* code does not cascade to its schools — `CODE_DIVISORS.SCHOOL_TO_DISTRICT` exists but there is no `cascadeDistrictCodeToSchools`. That gap is real, not an oversight you're misreading.
- `schools.district_id` is a real FK now, not a denormalized code copy — `schema.sql` explicitly dropped `School.districtCode` on the Postgres side ("в Postgres это JOIN"). If a caller needs the district's code alongside a school, join for it; there's nothing to keep in sync manually anymore.
- Moving a teacher to another school is a separate operation, `POST /teachers/:id/transfer` (`{ schoolId, codeSuffix?, studentsToTeacherId? }`, `teacher.usecase.ts::transferTeacher` validates, `teacher.service.pg.ts::transfer` writes in one transaction; spec `TRANSFERS_TASK.md`). One card, one account, the teacher's code becomes `newSchool.code * 100 + suffix` (old one in `code_change_logs`), `district_id` from the new school. His students do **not** follow: all of them (hidden too) go to one other teacher of the OLD school (`studentsToTeacherId`, required when there are any) and are recoded `target.code * 1000 + nnn` (`nnn` kept if free, else the smallest free), each change logged with `caused_by` = the moved teacher. `student_results` is never touched. `PUT /teachers/:id` with a different `schoolId` answers 400 — there is no "move together with students and results" mode. The same is **not** true for a school moving to another district — `school.usecase.ts` only swaps the FK, the school's code keeps the old district prefix.
- `services/student.service.pg.ts` `assignTeacherToStudent()` still derives teacher/school/district refs by decoding the student's own code (used when `studentResult.service.pg.ts` creates students as a side effect of Excel import, see below).

### Soft delete — `students`, `teachers`, `schools`, `districts` are VIEWS now (migration `037`, spec `SOFT_DELETE_TASK.md`)

Deleting a district / school / teacher / student hides it (and its descendants) instead of removing it; an admin brings the batch back from «Silinənlər». **There is no permanent delete, on purpose:** the FKs from `*_year_ratings` are `ON DELETE CASCADE`, so a real `DELETE` would wipe rows of closed academic years and break the `academic_year_closures` checksums.

- Physical tables are `students_all`, `teachers_all`, `schools_all`, `districts_all` (+ `deleted_at`, `deleted_by`, `deletion_id`). The names `students`, `teachers`, `schools`, `districts` are **views** `SELECT * FROM <x>_all WHERE deleted_at IS NULL`; every existing query, every `v_*` rating view and Kysely code keeps using them and never sees a hidden row. INSERT / UPDATE / DELETE ... RETURNING through a simple view work in Postgres. FKs of other tables (`student_results`, `*_year_ratings`, `users`, `achievement_files`, ...) point at the base tables. RLS is not an option: the app connects as the superuser `isim`.
- **Invariant: a live row never references a hidden one** (`students.teacher_id/school_id/district_id`, `teachers.school_id/district_id`, `schools.district_id`). That is why the ~30 `LEFT JOIN`s from a student up to teacher / school / district need no changes. Delete keeps it by cascading (district -> schools, teachers, students; school -> teachers + students of the school *and* students of other schools assigned to its teachers; teacher -> students); restore checks it and answers 409 «Əvvəlcə «<ad> (<kod>)» ... bərpa edin» if a restored row would point to a still hidden parent (the topmost one is named).
- `deletions` is the journal of batches (`entity_type`, `entity_id` of the root, `deleted_by`, `counts` = what was hidden together with the root, `restored_at/by`). Rows are never removed. `deletion_id` on an entity says which batch hid it; restore brings back exactly one batch, not rows that were deleted separately earlier. Bulk delete of students = one batch per student.
- `services/deletion.service.pg.ts` owns it all: `softDelete` (inside the caller's transaction), `deleteEntity` / `deleteEntities` (used by the `delete` / `deleteBulk` of the four `.pg.ts` services, `deleted_by` comes from `req.user.userId` through controller -> usecase), `restoreDeletion`, `listDeletions`, `assertCodeNotDeleted`. HTTP: `routes/deletion.routes.ts` -> `/api/deletions` (`GET ?type=&search=&page=&size=`, `POST /:id/restore`), admin / superadmin only. Delete and restore refresh the current year's `*_year_ratings` in the background (`refreshRatingsInBackground`, not awaited; a closed year is silently skipped).
- **Rule for migrations: `SELECT *` in a view is expanded at creation time.** Any migration that does `ALTER TABLE students_all ADD COLUMN ...` (same for the other three) must re-create the view (`CREATE OR REPLACE VIEW students AS SELECT * FROM students_all WHERE deleted_at IS NULL` is enough only when columns are appended; otherwise DROP + re-create and re-create the dependent `v_*` views), otherwise neither the code nor Kysely sees the column. Types for the base tables are `students_all` ... in `types/db.ts` (same interfaces).
- **Where `*_all` is read on purpose:** `deletion.service.pg.ts`; `utils/deleted-account.util.ts` (login and token refresh refuse an account whose student / teacher / school / district is hidden — 403 / 401 «Hesabınızın bağlı olduğu qeyd silinib...»; the `users` rows and their data stay, restore gives access back; an already issued access token lives out its 15 minutes); `create` / `update` code checks of the four services (409 «Bu kod silinmiş ... məxsusdur» — UNIQUE(code) lives on the base table, so a hidden entity keeps its code); `checkExistingDistrictCodes/SchoolCodes/TeacherCodes` (Excel directory imports skip codes owned by hidden rows; this also keeps them away from `INSERT ... ON CONFLICT (code) DO UPDATE`, which through a view would silently update the *hidden* row); `studentResult.service.pg.ts::processStudentResults` (a row whose student is hidden, or whose new student's teacher is hidden, is **rejected** with an error issue «Silinmiş şagird» / «Silinmiş müəllim», never restored by an upload); `utils/code-cascade.util.ts` and the student move in `teacher.service.pg.ts::transfer` (hidden descendants follow the code / school of a live parent, otherwise a restored student would carry a stale code); `gradePromotion.service.pg.ts` (hidden students are promoted too, so a student restored next year has the right grade; snapshots in `student_grade_history` as well).
- `v_student_year_scores` / `v_student_month_scores` are built from `student_results` alone (no join to students), so `stats.service.pg.ts::recomputeStudentRatings` joins the live `students` view — otherwise hidden students would be written into `student_year_ratings`. Teachers' / schools' / districts' sums go through the live views and need nothing.
- Not touched by a delete: `student_results`, `*_year_ratings` (closed years stay byte-identical, archive lists join live views so hidden entities just disappear from them), `issued_certificates` (QR verification keeps working), `achievement_files` and their files on disk, `profile_change_requests` (hidden from the moderation queue by `entityIsLive`, back after a restore), `users`. `utils/linked-users.util.ts` (`deleteLinkedUsers`) is gone. Regions have no soft delete.

### Rating chain — the core domain flow

Current-year scores are computed **on read** by SQL views over `student_results`; past years are frozen rows in five per-entity tables. `db/rating-semantics.md` is the authoritative account and is more current than this file for anything rating-related — read it first.

- Tables: `student_year_ratings`, `teacher_year_ratings`, `school_year_ratings`, `district_year_ratings`, `region_year_ratings` — history only, never recomputed for past years.
- Views for the current year: `v_student_year_scores` → `v_student_places`, `v_teacher_year_scores` → `v_teacher_places`, `v_school_year_scores` → `v_school_places`, `v_district_year_scores` → `v_district_places`, `v_region_year_scores` → `v_region_places`. `v_student_*` sum the student's results; teacher / school / district (year and month) views are built **straight from `student_results` by the result snapshot** (`student_results.teacher_id/school_id/district_id`, migration `038`, through the helper view `v_result_points`), not from the level below and not from the current links: points stay with the teacher / school / district where the exam was sat, so a transfer never moves them. The snapshot is taken by the trigger `student_results_snapshot` (student -> teacher -> teacher's school -> school's district) on every insert path; a re-upload of the same exam leaves it alone. A result counts at a level if the student and every snapshot entity up to that level are live. The region view still sums its districts. Each `*_places` view dense-ranks the scores. `/statistics` (`statistics.service.pg.ts`) deliberately stays on current links (it describes today's contingent). Details: `db/rating-semantics.md`, «Обновление 23.10.2026».
- **Places rank by raw `score`, not `average_score`, at every level** — settled in `013_ratings_by_raw_score.sql` after an earlier (wrong) decision to rank by average. `average_score` is still shown in the UI as a value, just not used for ranking. Zero/no-score entities get `place = NULL`, not a tail rank.
- Academic year is September–June; `utils/academic-year.util.ts` `getCurrentAcademicYear()`; `student_results.academic_year` is a generated column from `(month, year)` so July/August rows land in no academic year, same as the old `$or` logic.
- District average score = `score` / live number of students of the district (as for a region) since `035_average_places_and_district_average.sql` (owner's decision 22.10.2026); the Mongo-era divisor `students × schools` is gone, archive rows were recomputed. Teachers, schools and districts also store a second place by average score (`average_place`, plus `average_district_place` for teachers/schools) next to the raw-score `place`/`district_place`; the `filterPlace` column of the rating tables ranks by whichever metric the table is sorted by (`utils/rank-metric.util.ts`, reported as `filterPlaceBasis`).
- Name sorting uses `COLLATE az_ci` — a real Postgres collation defined in `schema.sql` (`locale = 'az-u-ks-level2'`), not a driver option. Azerbaijani ordering is a requirement, not decoration.
- **`ratedOnly=true`** (`FilterOptionsPg.ratedOnly`, sent only by the yearly `/stats` tabs and their Excel export; `DUZELISLER_2026-10-29_TASK.md` G1) narrows `GET /students` and `/api/stats/{teachers,schools,districts,regions}` — year and `month` branches alike — to entities whose rating row for the shown year/month and exam type has `score > 0`; rows, `filterPlace` and `totalCount` all go through the same condition. Without it every live entity is listed with an empty score tail (`LEFT JOIN *_year_ratings`), which the `/students` directory and the teacher profile's student list rely on — don't make it the default.
- `ratingYear.service.pg.ts` (`resolveRatingYear`) decides which academic year non-admins see on pages where the year isn't explicitly chosen (home cards, profiles) — backed by `app_settings` key `ratings.activated_academic_year` (migration `019_app_settings.sql`). Explicit `filters.academicYear` (e.g. the `/stats` page) bypasses it entirely; callers must opt in.
- `academic_year_closures` (migration `015`) freezes a finished academic year and stores per-table `count(*)`/`sum(score)` checksums so a later audit can prove the archive wasn't corrupted without a pre-migration dump. `academicYearClosure.service.pg.ts` both closes years manually and auto-closes finished ones on server startup (`index.ts`, non-fatal if it fails). Order is enforced: manual closure only in June-August (from September `getCurrentAcademicYear()` is already the new year), grade promotion refuses (409) until the outgoing year is closed, and auto-closure runs a final `updateAllStats(year)` before sealing only for the just-finished year and only if grades weren't promoted yet — originally because teacher / school / district sums followed live student links, so a post-promotion recompute distorted the archive. Since `038` those sums go by the result snapshot and student grades come from the results themselves (`031`), so the guard is now a safety net rather than a known distortion; keep it. Older years are never recomputed (2025/2026 pillə came from the customer's file by correct-answer count, not the percent scale).
- Exams have types as of migration `023_exam_types_and_level_scales.sql`: `exam_types` → `exam_type_sections` (grade ranges) → `exam_type_section_subjects` (just the subject set per section — see below), plus `level_scales`/`level_scale_bands` (percent-based pillə bands). `subjects` became a pure code lookup in the same migration. All existing exams sit on the single `is_base = true` type, and every current rating screen resolves through it — **nothing may leave zero rows with `is_base = true`**. Mid-rollout: `IMTAHAN_NOVLERI_TASK.md` (parent directory) is the live spec, check it before assuming the schema is final. The `5-11 sinif` section was created empty by `023` and got seeded (`az`/`math`/`english`) by `025d_question_counts_from_file.sql` — an admin can still add more subjects in the exam-type editor, same as for any new type.
- **Question counts are a property of the individual result, not of the exam type** (`IMTAHAN_NOVLERI_TASK.md` §16, migration `025d_question_counts_from_file.sql`). `exam_type_section_subjects.max_questions` and `exam_types.has_question_counts` are gone — the section config only defines *which* subjects belong to it. The denominator of `score_percent` is `Σ student_result_subject_scores.question_count` for that specific result, computed in `studentResult.service.pg.ts::computeScoreSummary` (manual create/update) and in `processStudentResultsFromExcel` (bulk import) — both require every subject to carry a positive `question_count`, or they throw/report a row error rather than silently dividing by zero. `resultTemplate.service.ts` always emits a `"<subject> (sual sayı)"` column per subject now, unconditionally.
- **`resultTemplate.service.ts`** (`IMTAHAN_NOVLERI_TASK.md` §18) is the single place that builds the results-template header/sheet — `generateForSection(examType, section)` does the actual work (column order since §18.2: all subject scores first, then all `"(sual sayı)"` counts — `studentResult.service.pg.ts::parseHeaderColumns` matches by name/suffix, not position, so order doesn't matter to the parser) and both public entry points call it: `generate(examId, grade)` (`GET /exams/:id/results-template.xlsx?grade=N`, §7 — resolves the section via the exam's type + grade) and `generateForType(examTypeId, sectionId)` (`GET /exam-types/:id/results-template.xlsx?sectionId=X`, §18.1 — resolves the section directly, no exam involved; same auth as `GET /exam-types`, any authenticated role). This file is also the **only** backend file on `xlsx-js-style` instead of the community `xlsx` package (§18.3, added as a backend dependency) — it needs `cell.s` styling (bold header row) and `!cols` widths (header text length + padding) that the community fork can't do; every other Excel-reading file in the backend stays on plain `xlsx` since reading doesn't need styles. Neither library can write frozen panes or data validations, so `addFreezeAndValidations` unzips the written workbook with `fflate` (direct dependency), splices `<pane>` into `<sheetView>` and `<dataValidations>` right after `</sheetData>` of `sheet1.xml` (Sinif = list of the section's grades, scores ≥ 0, question counts whole ≥ 1, rows 2..10001), and re-zips — verified to open in Excel without repair. A second sheet `Təlimat` describes the exam/type/section and the import rules; the parser reads only the first sheet, so `Nəticələr` must stay first. The exam-level template is named `netice-sablonu-<exam-slug>-<section-slug>.xlsx`; the frontend takes the name from `Content-Disposition` (exposed via `cors({ exposedHeaders })` for local cross-origin dev).

### Role-based data scoping — this is the security boundary

Every list/stat endpoint narrows its query by the caller's role, as an inline block duplicated across controllers (`student.controller.ts`, `teacher.controller.ts`, `school.controller.ts`, `district.controller.ts`, `stat.controller.ts`, `statistics.controller.ts`, `examResults.controller.ts` — `statistics.controller.ts`'s version, `applyRbacFilters`, is the most carefully commented one and worth reading first):

```
regionRepresenter    → filters.districtIds = districtIdsOfRegion(req.user.regionId)  (region-scope.util.ts)
districtRepresenter  → filters.districtIds = [req.user.districtId]
schoolDirector       → filters.schoolIds   = [req.user.schoolId]
teacher              → filters.teacherIds  = [req.user.teacherId]
student               → only their own record
```

`regionRepresenter` is a role added after the original 4-role design — it carries only `regionId` in the JWT, so every scoping site has to expand it to `districtIds` via `districtIdsOfRegion()`. If you add a new scoped role, every one of these controller blocks needs updating, and the frontend's `core/config/rbac.config.ts` needs a value for every permission key (a missing key there is a silent bug, not a compile error). Newer scoping code (`statistics.controller.ts`) only strips filters *above or outside* the caller's scope and leaves narrower ones alone (AND-ing them is safe) — this fixed a real bug where a school director opening a teacher's profile saw school-wide numbers instead of that teacher's. Older scoping sites may not have this refinement; check before assuming.

`req.user` is populated by `middleware/auth.middleware.ts` from the JWT. The frontend's RBAC config only hides UI — **row-level scoping is enforced here and nowhere else**.

Auth: JWT access + refresh, refresh tokens stored server-side (max 5 sessions) and sent as an httpOnly cookie. `controllers/auth.controller.ts` + `services/token.service.pg.ts`.

### Login/activity statistics (admin only)

### Column settings (`user_settings`)

`services/userSettings.service.pg.ts`, routes `/api/user-settings`. Two kinds of rows in one table: a user's own row (`user_id` set; `GET/PUT /user-settings` always read/write the caller's row by JWT — the frontend's `userId` is ignored) holds an admin's own column sets in the `*_collumns` text[] columns (misspelling kept on purpose, the frontend uses it); the single global row (`user_id IS NULL`, `GET /global` any role, `PUT /global` admin/superadmin) holds `role_settings` jsonb — per role, per tab, a list of column keys. `PUT /global` replaces `role_settings` as a whole, so the backend never needs to know the tab keys: new tabs such as `profileRatings` (columns of the profile's «Reytinqlər» table, `DUZELISLER_2026-10-29_TASK.md` G2) need no backend change. `exam_result_collumns` (migration `041`) is the admin's own `/exam-results` column set; empty = the page's default. A new own column set = migration + `schema.sql` + `types/db.ts` + the three mappings in the service (`UserSettingsRow`/`UserSettingsUpdate`, `toColumns`, `toRow`).

## Traps

- **Zero tests. Transactions exist, but are opt-in per write path.** `pg.transaction().execute()` is used in ~10 services (`academicYearClosure`, `district`, `exam`, `examType`, `gradePromotion`, `profileChangeRequest`, `region`, `school`, `student`, `teacher` — all `.pg.ts`) for multi-statement writes that must be atomic (mainly the code cascades and closures). Anything not listed there still isn't wrapped — check the specific service before assuming atomicity.
- **`express-validator` is a dependency but used in `auth.controller.ts` only.** Everywhere else validation is ad-hoc via `ValidationUtils`. Follow `ValidationUtils` unless you're in auth.
- **A global `errorHandler` middleware exists** (`middleware/errorHandler`, imported in `index.ts`) but is effectively bypassed: all 23 controllers wrap their methods in their own try/catch (~184 blocks). Match the surrounding style rather than half-migrating a file to the global handler.
- **`src/_backups_ratings_migration/` is dead code** — `.backup` copies from the ratings migration. It sits inside `src/` and gets compiled. Never edit, never import; it is not a reference for current behavior.
- Request body limit is 100 MB (`index.ts`) for Excel/bulk uploads. File-upload routes put `authMiddleware` **before** `upload.single(...)` and their multer instances have a 50 MB `fileSize` limit (`LIMIT_FILE_SIZE` → 413 in `errorHandler`) — multer first would let anonymous requests write to `uploads/temp/` and leave the file behind on 401. Keep that order on new upload routes.
- An exam's **type and date are both locked once it has results** (`exam.service.pg.ts::update`, 409). `student_results.month/year` are copied from the exam date at import, so a later date change would move results into another month/academic year. The date comparison is by calendar day in `Asia/Baku`: older exams edited through the frontend dialog are stored at 20:00Z of the previous day, and re-saving the same day must neither trip the lock nor rewrite the timestamp.
- `POST/PUT /exam-types` bodies are validated up front in `examType.controller.ts::validateExamTypeBody` (grades 1-11, no overlapping sections, no empty/duplicate subjects), and leftover constraint violations are mapped to readable 4xx by `mapExamTypeDbError`. `upsertSections` parks kept sections on unique negative grade ranges before writing the real ones — the EXCLUDE constraint is checked per statement, so moving a boundary between two sections would otherwise fail.
- **Exam-type sections are versioned by academic year** (migration `040`: `from_year`/`to_year` inclusive, NULL = unbounded, plus `sort_order` = array index of the PUT body). The editor sends only current sections (`archived` = `to_year` < current year is read-only history; sending its id → 400). In `upsertSections`, a current section that has results from past academic years and gets new grades, a new subject set or is removed is **archived** (`to_year = current - 1`, id/subjects/results kept) and the incoming entry is inserted as a new section from the year after the overlapping archive; otherwise it is updated in place / deleted. Afterwards every result of the current year and later is re-pointed to the section covering its grade in its year, and any leftover → 409 (rollback). Never resolve a section by `(type, grade)` alone — use `findSectionForGrade(db, type, grade, academicYear)` / `isSectionInForce` with the exam's year (`academicYearOfDate` / `academicYearOfMonth` in `academic-year.util.ts`, July/August → the year just ended, as the import does). Ratings never read `section_id`.
- Startup loads one in-memory cache before listening (`loadLevelScaleBandsCache` in `services/levels.cache.ts`) — if you add a row to `level_scale_bands`/`level_scales` at runtime via direct SQL, the server won't see it until restart. `getBands(scaleId)`/`getBandsByScaleCode(code)` are the only source of truth for pillə now — the old `levels` table and its cache (`loadLevelsCache`/`getLevelsCache`/`getLevelByCode`/`getLevelByScore`) are gone as of `026_drop_legacy_subject_columns.sql` (`IMTAHAN_NOVLERI_TASK.md` §20).

## Excel

Reading is server-side via `services/excel.service.ts` (`readExcel`, `xlsx` package). **Students are created as a side effect of importing exam results**: `services/studentResult.service.pg.ts` inserts any student code it doesn't find (deriving teacher/school/district from the code itself — teacher = code / 1000, resolved in one batched query). There is no standalone "register students" importer, and student codes always arrive from the file — nothing generates them server-side.

Results import (`processStudentResultsFromExcel`, rules from `IMTAHAN_NOVLERI_AUDIT_2026-10-05_TASK.md` group 2 in the parent directory):
- **One file = one section.** Rows whose grades fall into different sections of the exam type fail the whole file; the file's subject columns must equal the section's subject set exactly (a missing subject used to shrink the percent denominator silently). Headers match subject `name_az` case- and whitespace-insensitively.
- Row-level problems come back in `studentsWithIncorrectResults` as `{ row, code, reason }` (`row` = Excel row number, `code` null when the code cell itself was bad); valid rows still import. `questionCountWarnings` flags rows whose question count differs from the file's most common value for that subject — a warning only, §16 allows different lengths.
- The write is **one transaction** and batched (chunked multi-row upsert, prior band ranks in one query via `levelScale.service.pg.ts::maxPriorBandRanks`, bands from the startup cache via `resolveBandCached`): a failure leaves neither results nor newly created students. The response carries `processedCount`, not the result rows.
- `issues: ImportIssue[]` is the complete per-cell report — every error and warning with Excel row, column letter + header text, student code/name, the raw cell value, a short Azerbaijani `kind` and `message`, `severity`. The frontend turns it into a downloadable .xlsx (`ExcelService.exportImportIssues`) so a district keeps the list after the dialog closes; the older per-kind lists stay for the dialog itself.
- **Old codes** (`TRANSFERS_TASK.md` §5, `resolveOldStudentCodes`): a code that belongs to no student and whose teacher part (`code / 1000`) belongs to no teacher (hidden ones count) is looked up as `old_code` of a student in `code_change_logs` (latest entry); the row is written to the current student with a warning issue «Köhnə kod». A hidden student is rejected as «Silinmiş şagird»; the same student present under both codes: the later row is rejected («Təkrar şagird»). The result snapshot (teacher / school / district) is taken by a DB trigger on insert; re-uploading an exam does not change it.
- `month`/`year` of the results are the exam's calendar day in `Asia/Baku`, not `getUTCMonth()` — most exams are stored at 20:00Z of the previous day.
- `DELETE /api/exam-results?<filters>` (admin/superadmin, `examResults.service.pg.ts::deleteExamResults`) deletes everything the `/exam-results` filter shows — the frontend's «Filtrə uyğun nəticələri sil» button, used to delete a district's rows of an exam before re-uploading a corrected file. It requires at least one `examIds` and refuses (409) if any matching result is in a closed academic year; then `refreshRatingsInBackground()`. `DELETE /api/exam-results/selected` (body `{ ids }`, max 5000, `deleteExamResultsByIds`, 30.10.2026) deletes the rows ticked in the table («Seçilmişləri sil»); ids travel in the body because a selection across pages may not fit a URL. Both share `deleteMatching` — same closed-year 409, chunked delete, `students.status` reset and rating refresh.
- `/exam-results` year restriction (`DUZELISLER_2026-10-29_TASK.md` G3, customer decision 30.10.2026): every role except admin/superadmin — **moderator included**, so the check is an explicit `role === 'admin' || role === 'superadmin'` (`isYearRestricted`), not `isAdminLike` — gets `academicYear = getCurrentAcademicYear()` forced in `parseScopedFilters` (filter `sr.academic_year`), and `GET /:id` answers 404 for another year's result. Deliberately not `resolveRatingYear()`: that one lags until the new year's ratings are activated, while the customer means the calendar academic year. The Excel export on that page is client-side from the list response, so it is covered too. `GET /api/exam-results/latest-exam?<same filters>` returns `{ examId }` — the latest exam (by date, then id) with at least one result in the caller's scope; the page preselects it.
- `POST /student-results/import-json` (one-off legacy JSON import) is gone — it failed on every record (`month: 0` vs the CHECK).
