# Цепочка рейтинга: что делает код сегодня

Составлено Opus 5, 04.08.2026, чтением `stats.service.ts`, `utils/stats.utils.ts`, `utils/ranking.util.ts`.
Нужно затем, что схема Postgres и views (`db/schema.sql`) обязаны воспроизвести это **дословно**, включая странности. Без этого документа расхождения в differential-проверке будут выглядеть как ошибки миграции, хотя это поведение оригинала.

Уточняет `MONGO_TO_POSTGRES.md` §3 — там часть деталей описана неточно (см. «Поправки» в конце).

## Два несовместимых пути расчёта — главная находка

**Решено 04.08.2026: официальный путь для Postgres — путь B (по среднему баллу).** Views `v_teacher_places`/`v_school_places`/`v_district_places` в `schema.sql` уже переписаны под это (фильтр `average_score > 0`, без `district_place`); реализация в `stats.service.ts` должна писать `*_year_ratings` по той же логике. Ниже — таблица различий как историческая справка о том, откуда взялось решение.

Одни и те же поля (`ratings[year]`, `place`, `score`, `averageScore`) пишутся двумя независимыми механизмами. Побеждает тот, который вызвали последним.

| | **Путь A — иерархический** | **Путь B — плоский** |
|---|---|---|
| Точка входа | `StatsService.updateAllStats()` (`stats.service.ts:355-373`) | `updateEntityStats()` (`utils/stats.utils.ts`) из `district/school/teacher.service.ts:20-22` |
| Триггер | пересчёт статистики после импорта результатов | эндпоинты `updateDistrictsStats` / `updateSchoolsStats` / `updateTeachersStats` |
| Балл учителя | Σ баллов его учеников | Σ баллов его учеников — **совпадает** |
| Балл школы | Σ баллов **учителей** школы | Σ баллов **учеников** школы — арифметически то же |
| Балл района | Σ баллов **школ** района | Σ баллов **учеников** района — то же |
| Средний балл | ÷ сохранённый `studentCount` сущности | ÷ сохранённый `studentCount` сущности — **совпадает** |
| Средний балл **района** | ÷ `учеников_в_районе × школ_в_районе` | ÷ `studentCount` района |
| Место | dense rank по **`score`** | dense rank по **`averageScore`** |
| Кто без места | никто (нули тоже ранжируются) | все с `averageScore = 0` получают `place = null` |
| Пишет `districtPlace` | да | **нет** |
| Пишет плоские `place`/`score` | да | нет, только внутрь `ratings[]` |

**Что с этим делать.** Views в `schema.sql` реализуют **путь A**. Путь B не реализован сознательно: две взаимоисключающие реализации одного поля в реляционной схеме воспроизвести нельзя, да и не нужно.

Это вопрос к заказчику, а не техническое решение: *какое место считается настоящим — по сумме баллов или по среднему?* Ответ определяет и то, останется ли `average_score` районов в UI (сейчас он занижен, см. ниже). До ответа миграцию можно готовить, но не переключать.

## Точная семантика пути A (то, что воспроизводят views)

**Ученик, баллы** (`stats.service.ts:1216`)
`score` = сумма четырёх слагаемых (`participationScore + developmentScore + studentOfTheMonthScore + republicWideStudentOfTheMonthScore`) по результатам внутри окна учебного года (сентябрь–июнь).
`averageScore` = `score / participationCount`, где `participationCount` — число результатов в окне.
Отсутствующие слагаемые считаются нулём (`$ifNull`).

**Ученик, места** (`stats.service.ts:1312`)
Dense rank по **`score`**, отдельно **внутри каждого класса**. `districtPlace` — внутри класса и района.
Фильтра «> 0» нет: ученик с нулевым баллом место получает. У учеников без поля `score` вообще места нет.
`grade: null` и `district: null` в Mongo схлопываются в отдельную группу — в SQL `PARTITION BY` с NULL ведёт себя так же. Единственное расхождение: Mongo приводит `grade: null` к `0` и смешивает их с реальным нулевым классом, SQL — нет. Классов «0» в базе нет, так что практического эффекта не ожидается.

**Учитель** (`stats.service.ts:1403`)
`score` = Σ плоских `score` его учеников. `averageScore` = `score / teacher.studentCount` — по **сохранённому полю**, не по числу найденных учеников. Если `studentCount` устарел, средний балл неверен; это намеренно оставлено как есть.
Места (`:1466`) — dense rank по `score`, республиканское и внутри района, без фильтра «> 0», tie-break сортировки по `code` (на значение места не влияет, только на порядок в массиве).

**Школа** (`stats.service.ts:1556`) — Σ `ratings[текущий год].score` её **учителей**, делённая на `school.studentCount`. Места — как у учителей.

**Район** (`stats.service.ts:1723`) — Σ `ratings[текущий год].score` его **школ**.
Делитель среднего балла — **ошибка в пайплайне**: `$lookup` подтягивает к каждой школе всех учеников района (`localField: 'district'`, `foreignField: 'district'`), после `$group` делитель оказывается равен `учеников_в_районе × школ_в_районе`. Средний балл района занижен ровно во «столько раз, сколько в районе школ».
На места это не влияет (они по `score`), но цифра видна в интерфейсе. В `v_district_year_scores` воспроизведено дословно, правильный вариант рядом закомментирован.

**Год** во всех `ratings[]` — год **начала** учебного года (`getCurrentAcademicYear()`: месяцы 1–8 → предыдущий год).

**Сортировка по ФИО** — `.collation({ locale: 'az', strength: 2 })`, 4 места в `stats.service.ts`.

## Поправки к MONGO_TO_POSTGRES.md

Документ писался до чтения всех четырёх уровней; расходится с кодом в четырёх местах:

1. §3.1 «`average_score > 0` обязательно» — верно только для `updateEntityPlaces` (путь B). В пути A фильтра нет.
2. §3.1 ранжирование учеников — по `score`, а не по `average_score`. Учителя и школы — тоже по `score`, хотя средний балл у них считается.
3. §3.1 не упоминает, что учителя, школы и районы в пути A ранжируются по `score`, а в пути B по `average_score`. Это и есть конфликт выше.
4. §3.4 про деление на `studentCount` — верно, но у района проблема другая и крупнее: делитель вообще не число учеников.

## Что не проверялось

Оба пути пишут только текущий учебный год. Как заполнялись `ratings[]` за прошлые годы — из истории кода не восстанавливается, поэтому исторические строки переносятся ETL как есть и **не пересчитываются** views.

## Обновление 13.08.2026 — district_place досчитан для учителей и школ

Таблица выше («Пишет districtPlace: путь A — да, путь B — нет») отражает состояние на 04.08.2026,
когда решался вопрос «путь A или B» — оставлена как есть, это историческая справка. По факту
с 13.08.2026 (`007_teacher_school_district_place.sql`) `v_teacher_places`/`v_school_places`
считают `district_place` той же dense_rank-логикой, что и `v_student_places` (по `average_score`,
партиция по `district_id`) — решение пользователя, раз UI-колонка есть у обеих сущностей, а «—»
выглядело как баг переноса, а не как сознательный пробел пути B.

## Обновление 20.08.2026 — «путь B по average_score» отменён: место везде по score

Решение от 04.08.2026 («официальный путь — B, по среднему баллу») оказалось **неверным
пониманием требования заказчика**, а не его сознательным выбором. Уточнение: все рейтинги мест —
İlin şagirdləri, İlin müəllimləri, İlin məktəbləri, İlin rayonları, регионы (RTİ) — считаются по
**сырому `score`**, кроме İnkişaf (отдельный помесячный механизм `markDevelopingStudents`,
никак не пересекается с dense_rank по местам — не затронут).

Ученики (`v_student_places`) уже считали место по `score` — путь A для них не менялся ни разу,
это было верно с самого начала. Реально изменились только `v_teacher_places`, `v_school_places`,
`v_district_places`, `v_region_places` (`013_ratings_by_raw_score.sql`): `ORDER BY average_score
DESC` → `ORDER BY score DESC`, `WHERE average_score > 0` → `WHERE score > 0`. Правило «нулевые не
попадают в рейтинг (place = NULL, а не место в хвосте)» — отдельное решение, не пересматривалось.

`average_score` как значение (для отображения «Orta reytinq xalı» в UI) остаётся как есть — не
используется только для ранжирования.

Побочно поправлен `getDistrictStatistics` (`stats.service.pg.ts`) — единственное место, где
`place` считался не из персистентной view, а на лету под колонку сортировки; дефолт (без явной
сортировки по `averageScore`) был `average_score`, стал `score` — иначе `/stats` (районы) при
первой загрузке показывал бы место, расходящееся с профилем района.
