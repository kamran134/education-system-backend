- `003_student_result_status.sql` (`student_results.status` как generated-колонка от `development_score`) указан в README и в `KNOWN_APPLIED` скрипта `apply-pending.sh`, но файла в каталоге нет. Он считается применённым на проде вручную, а `db/schema.sql` его уже содержит (комментарий в `apply-pending.sh`).
- `009_student_year_scores_single_grade.sql` / `031_student_year_scores_single_grade_again.sql`: любое `CREATE OR REPLACE` или пересоздание `v_student_year_scores` с `grade` в `GROUP BY` ломает «Reytinqləri yenilə» (2 строки на ученика, падение на PK `student_year_ratings`, таблица остаётся пустой). Фикс уже терялся один раз (в 025); при переписывании вьюхи его нужно сохранять.
- `021_monthly_rating_views.sql` / `022_student_month_scores_one_row.sql`: запущенная на проде миграция не правится «на месте» — `apply-pending.sh` сверяется по имени файла и не перезапустит её. Исправление делается только новым файлом. Месячный срез намеренно без `average_score` на всех уровнях.
- `024_student_result_subject_scores.sql`: расхождение сохранённого `level` и шкалы `isim_percent` у результатов с `total_score` 15, 25, 47 — ожидаемое, не баг; старые pillə выданы по прежним абсолютным порогам и заморожены. Пересчитывать и «выравнивать» не нужно.

- `025d_question_counts_from_file.sql`: числа `max_questions` из конфига типов экзаменов уничтожаются безвозвратно (возврат только из `pg_dump`). Обязательность `question_count` обеспечена кодом (`computeScoreSummary`, `processStudentResultsFromExcel`), а не CHECK, чтобы не блокировать историю.
- `026_drop_legacy_subject_columns.sql`: единственная миграция без пути отката кроме дампа. `tsc` не поймал бы запрос `importLegacyResultsFromJson` (объект с лишними полями через промежуточную переменную) и raw SQL в `certificate-issue.service.ts` — их нашли и исправили вручную до применения. Если код ссылается на таблицу в сыром `sql` шаблоне, компилятор этого не видит.
- `025b_student_fullname.sql`: порядок склейки ФИО — фамилия, имя, отчество. Склейка необратима, поэтому три старые колонки жили рядом как путь отката и были удалены только в 026. Номер с буквой `b` выбран, чтобы не занимать зарезервированный 026; порядок применения определяется именем файла.
- `032_reseal_2025_closure_checksums.sql`: пломба 2025 была снята авто-закрытием с неполного архива (авто-закрытие пересчёт не делает «by design»), поэтому её перезаписали по текущему содержимому. Рейтинги 2025 после этого не пересчитывать: они посчитаны по правилам того года (pillə из файла заказчика), пересчёт по процентной шкале исказил бы их.
- `033_student_gender.sql`: пол выведен эвристически по ФИО, а не взят у заказчика; 74 спорных случая решены вручную по правилам владельца (список в CSV вне git, там полные имена). `NULL` отображается как мужской. Для учеников, созданных после экспорта, пол определяет импорт.
- `035_average_places_and_district_average.sql`: среднее района в архиве `district_year_ratings` пересчитано по ТЕКУЩЕМУ числу учеников района (для всех лет и типов экзаменов). Это допустимо, потому что пломбы 015 хранят только `count(*)` и `sum(score)`; `score` и места по сырому баллу не менялись.
- `037_soft_delete.sql`: `students`/`teachers`/`schools`/`districts` теперь вьюхи; `SELECT *` во вьюхе раскрывается при создании, поэтому любая будущая `ALTER TABLE <x>_all ADD COLUMN` обязана пересоздать вьюху `<x>`. `UNIQUE(code)` живёт на базовой таблице, скрытая сущность держит свой код, а `INSERT ... ON CONFLICT (code) DO UPDATE` через вьюху молча обновил бы скрытую строку.
- `037_soft_delete.sql`: настоящего удаления нет специально — FK из `*_year_ratings` с `ON DELETE CASCADE` стёр бы строки закрытых лет и сломал пломбы. Родительские вьюхи привязываются к `*_all` по OID после `RENAME`, поэтому миграция пересоздаёт их динамически (определения захватываются до переименования).
- `038_result_snapshot.sql`: снапшот `teacher_id`/`school_id`/`district_id` строится по цепочке student -> teacher -> школа учителя -> район школы, а не по `students.school_id`/`district_id`. Повторная загрузка того же экзамена (`ON CONFLICT (student_id, exam_id) DO UPDATE`) снапшот не меняет; для закрытых лет бэкфилл по текущим связям — лучший доступный источник.
- `013_ratings_by_raw_score.sql` / `035_average_places_and_district_average.sql`: места ранжируются по сырому `score` (013), а `average_score` показывается как значение; с 035 рядом лежит вторая метрика места `average_place`. Нулевые и безбалльные сущности получают `place = NULL`, а не хвост рейтинга; у учеников фильтра «> 0» нет.

## Механика применения

- Отслеживание: `apply-pending.sh` создаёт (если нет) таблицу `schema_migrations (filename text PRIMARY KEY, applied_at timestamptz)`; миграция считается применённой, если её имя файла есть в таблице (правка файла после применения БД не изменит).
- Порядок: все `*.sql` каталога по имени файла, по одному, пропуская уже записанные; суффиксные файлы (`025b`, `025c`, `025d`) встают после `025`.
- Bootstrap: если `schema_migrations` пуста, в неё без запуска SQL записываются `KNOWN_APPLIED` (`001`, `001b`, `002`, `003`) — они были применены вручную до автоматизации. Скрипт рассчитан на одну живую прод-БД; свежая база из `db/schema.sql` через него не проходит.
- Бэкап: перед КАЖДОЙ реально применяемой миграцией — `pg_dump -F c` внутри контейнера и копирование дампа в `~/rollback/pg-pre-<файл>-<timestamp>.dump` на сервере. Пропуска бэкапа нет.
- Подключение: всё идёт через `docker exec` в контейнер Postgres (имя в переменной `CONTAINER`, значение `isim-pg`), с `DB_USER`/`DB_NAME` в скрипте; хост и пароль в скрипте не заданы (подключение внутри контейнера).
- Ошибки: `set -euo pipefail` плюс `psql -v ON_ERROR_STOP=1`; на первой же ошибке скрипт останавливается, шаг CI (`.github/workflows/docker.yml`) падает, деплой контейнера бэкенда не происходит, старый продолжает работать. Запись в `schema_migrations` делается только после успешного применения.
- Транзакции: скрипт сам транзакцию не открывает; каждый файл обязан быть обёрнут в `BEGIN; ... COMMIT;` (требование README), и применяется целиком одним вызовом `psql` как одна транзакция — упавшая миграция откатывается Postgres. Восстановление из дампа нужно, только если проблема обнаружена уже после коммита. `029` из-за этого без `CONCURRENTLY`.
- Запуск: автоматически — при каждом push в `main` (CI копирует каталог на сервер и вызывает скрипт). Вручную: бэкап `docker exec isim-pg pg_dump -U isim -d isim -F c ...`, затем `docker exec -i isim-pg psql -U isim -d isim < db/migrations/NNN_name.sql`; ручной способ нужен для экстренных хотфиксов без нового образа.
- Локально: `apply-pending.sh` жёстко привязан к контейнеру `isim-pg` и `~/rollback`, поэтому для локальной базы применяют файлы вручную через `psql` (например, в локальном контейнере/кластере); автоматически на чужую БД скрипт не нацелить без правки констант.
- Требования к файлам: шапка (что, зачем, дата, задача), `BEGIN/COMMIT`, только вперёд (нетривиальный откат — рядом `NNN_name_rollback.sql`), идемпотентность желательна, но не в ущерб ясности. `db/schema.sql` после подтверждённой миграции приводится в соответствие вручную.
