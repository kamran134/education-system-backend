# 7. Деплой и эксплуатация

> Секретов (паролей, ключей, адресов серверов) в этом документе нет и быть не должно:
> репозитории публичные. Здесь только имена переменных и где их задавать. Доступы передаёт
> владелец.

## Топология

Один VPS (Европа), Docker Compose-проект в `~/isim` на сервере. `docker-compose.yml` и
`nginx.conf` лежат только на сервере, в git их нет.

```
интернет ──443──► nginx-proxy (nginx:latest, TLS Let's Encrypt)
                    ├── /           → frontend-app:80   (nginx:alpine со статикой SPA)
                    ├── /api/       → backend-app:5000  (Node, этот репозиторий)
                    ├── /auth/      → backend-app:5000
                    └── /uploads/   → backend-app:5000
                  backend-app ──► isim-pg (postgres:17-alpine)
```

| Сервис compose | Контейнер | Образ | Важное |
|---|---|---|---|
| `backend` | `backend-app` | `ghcr.io/kamran134/education-system-backend:latest` | `mem_limit: 200m`; порт `127.0.0.1:5000`; volume `~/uploads:/app/uploads`; переменные из `~/isim/.env` |
| `frontend` | `frontend-app` | `ghcr.io/kamran134/education-system-frontend:latest` | `mem_limit: 64m` |
| `nginx` | `nginx-proxy` | `nginx:latest` | порты 80/443; `./nginx.conf` смонтирован read-only; `/etc/letsencrypt` |
| `pg` | `isim-pg` | `postgres:17-alpine` | `mem_limit: 200m`, `shared_buffers=64MB`, `max_connections=50`; данные в `~/pg-data` |

- HTTP → HTTPS, `newisim.kpm.az` → `isim.kpm.az` (301).
- Для `/api` перед бэкендом ровно один прокси, отсюда `trust proxy = 1` в `index.ts`.
- `nginx-proxy` резолвит апстримы через Docker DNS (`resolver 127.0.0.11`) и `proxy_pass` с
  переменной. Без этого после пересоздания контейнера бэкенда nginx держал старый IP и отдавал 502.
- Файлы пользователей живут на хосте в `~/uploads`, переживают пересоздание контейнера.

## CI/CD

Деплой — **каждый push в `main`** в любом из двух репозиториев. Промежуточных стендов нет: `main`
это прод.

### Бэкенд (`.github/workflows/docker.yml`)

1. Сборка образа и push в GHCR с тегом `latest` (других тегов нет).
2. Запись `~/isim/.env` на сервере **из секретов GitHub**. Файл перезаписывается при каждом деплое.
   Править `.env` на сервере руками бесполезно: меняйте секрет репозитория.
3. Копирование `db/` на сервер и запуск `db/migrations/apply-pending.sh` (см. ниже).
4. Если миграции прошли: `docker compose pull backend && docker compose up -d --force-recreate backend`
   под `flock -w 600 /tmp/isim-deploy.lock`.

Секреты репозитория бэкенда: `GHCR_PAT`, `SSH_PRIVATE_KEY`, `SERVER_USER`, `SERVER_HOST`,
`JWT_SECRET`, `JWT_REFRESH_SECRET`, `PG_URL`, `PG_PASSWORD`, `MONGO_URI` (наследие, не читается).
В `.env` также пишутся `NODE_ENV=production` и `PORT=5000`. `FRONTEND_URL` и `CORS_ORIGINS` не
передаются: работают значения по умолчанию из кода.

### Фронтенд

Тот же сценарий без миграций: сборка образа (`ng build` внутри Docker) → GHCR →
`docker compose pull frontend && docker compose up -d frontend` под тем же `flock`. Секреты:
`GHCR_PAT`, `SSH_PRIVATE_KEY`, `SERVER_USER`, `SERVER_HOST`.

### Гонка двух репозиториев

Оба воркфлоу делают `docker compose` над одним проектом, а параллельные операции compose
небезопасны (19.08.2026 деплой упал с `removal of container ... is already in progress`).
`concurrency` в GitHub Actions работает только внутри одного репозитория. Межрепозиторную
сериализацию даёт общий файловый замок на сервере (`flock /tmp/isim-deploy.lock`, ожидание до 10
минут). Всё равно лучше пушить по очереди: сначала бэкенд, дождаться деплоя, потом фронтенд.

## Миграции при деплое

`db/migrations/apply-pending.sh` выполняется на сервере против контейнера `isim-pg`:

1. Заводит `schema_migrations (filename, applied_at)`, если её нет.
2. Берёт все `db/migrations/*.sql` **по порядку имён** и пропускает те, чьё **имя файла** уже есть
   в таблице.
3. Перед каждой применяемой миграцией делает `pg_dump` в `~/rollback/pg-pre-<файл>-<время>.dump`.
4. Применяет файл через `psql -v ON_ERROR_STOP=1` и записывает имя в `schema_migrations`.
5. На первой ошибке останавливается. Шаг CI падает, контейнер бэкенда **не обновляется**, старый
   продолжает работать на старой схеме.

Правила, вытекающие из механики:

- **Запушенную миграцию нельзя править.** Раннер сверяется по имени. Изменённый файл он не
  перезапустит: репозиторий поменяется, база нет, и расхождение всплывёт позже. Исправление —
  только новым файлом (пример: `021` → `022`).
- Исключение — миграция, которая **упала**. Она откатилась целиком и в `schema_migrations` не
  записана, такой файл можно исправить и запушить снова.
- Каждый файл сам оборачивается в `BEGIN; ... COMMIT;`. Шапка: что делает, зачем, дата, какое
  решение реализует. Только вперёд. Если откат нетривиален, рядом кладётся `NNN_name_rollback.sql`.
- Нумерация: следующий свободный трёхзначный номер (сейчас последняя — `038`). Буквенный суффикс
  (`025b`) — только если номер занят зарезервированной миграцией. Порядок определяется сортировкой
  имён.
- После подтверждённой миграции вручную обновите `db/schema.sql` (снимок итоговой схемы) и таблицу
  в `db/migrations/README.md`.
- Перед пушем прогоните миграцию на **локальной копии прода** ([02-local-setup.md](02-local-setup.md)).
  Миграция с данными, выведенными из продовой базы, тоже деплоится автоматически, проверяйте её
  особенно тщательно.
- Если миграцию пришлось применить на проде руками (экстренный хотфикс), **до следующего пуша**
  вставьте её имя в `schema_migrations`. Иначе автодеплой попытается применить её повторно и упадёт.
- После `ALTER TABLE <x>_all ADD COLUMN` пересоздайте вьюху `<x>`
  ([06-features.md](06-features.md#soft-delete-и-silinənlər)).
- После правки `level_scales`/`level_scale_bands` нужен перезапуск бэкенда (кэш). Деплой его и так
  делает.

Справочник всех миграций — [reference/migrations.md](reference/migrations.md).

## Как проверить, что версия доехала

Время коммита — не время деплоя: пуш может случиться позже, сборка идёт несколько минут.
Проверяйте то, что реально запущено:

```bash
# когда собран образ, который сейчас на сервере
docker inspect -f '{{.Created}}' ghcr.io/kamran134/education-system-backend:latest
# когда поднят контейнер и сколько раз перезапускался
docker inspect -f '{{.State.StartedAt}} {{.RestartCount}}' backend-app
# есть ли новый код внутри контейнера
docker exec backend-app grep -c '<новый идентификатор>' dist/<файл>.js
```

- Красный CI на шаге деплоя ещё не значит, что прод на старом коде. 19.08.2026 контейнер успел
  подняться на новом образе, а упала только уборка старого. Сначала проверьте контейнер.
- Снаружи: несуществующий маршрут `/api/...` отвечает 404 «Məlumat tapılmadı», существующий без
  токена — 401. Так можно проверить, что новый эндпоинт есть на проде.
- Фронтенд: `index.html` отдаётся с `no-cache`, бандлы с хешем в имени кэшируются на год. После
  деплоя достаточно обычной перезагрузки страницы.

## Бэкапы

| Что | Где | Как | Хранение |
|---|---|---|---|
| БД ежедневно | `/root/backups/pg_isim_<дата>.dump` | крон 02:30, `/root/scripts/backup-pg.sh` (`pg_dump -Fc` из `isim-pg`), лог `/var/log/pg-backup.log` | 14 дней |
| БД перед миграцией | `~/rollback/pg-pre-<файл>-<время>.dump` | `apply-pending.sh` | бессрочно, без ротации |
| Файлы пользователей (`~/uploads`) | — | **не бэкапятся** | — |

Риски, о которых нужно знать:

- Все бэкапы лежат **на том же сервере**. Внешней копии нет: потеря диска или сервера — потеря
  данных. Минимум, что стоит сделать, — регулярно забирать свежий дамп и `~/uploads` на другую
  машину.
- `~/uploads` (фото, фоны сертификатов, файлы «Uğurlar») не входит в бэкап.
- В `~/backups` остались `kpm_*.gz` эпохи MongoDB, а в `~/isim` — `db_backup*.gz`. Это исторические
  артефакты, к работе системы отношения не имеют.

Восстановление из дампа — `pg_restore` в **пустую** базу (`--no-owner --role=isim`). Перед
восстановлением прода остановите `backend-app`, чтобы он не писал в базу.

## Плановые задачи на сервере (crontab)

| Когда | Что | Последствия |
|---|---|---|
| ежедневно 02:30 | бэкап БД | — |
| ежедневно 03:00 | `docker system prune -f -a` | удаляет неиспользуемые образы; откат на «предыдущий образ» после этого невозможен |
| 1-е число, 03:00 | `docker compose down`, `certbot renew`, `docker compose up -d` | несколько минут простоя раз в месяц; на старте бэкенд закрывает завершённые учебные годы |

## Логи

- `docker logs backend-app`. В production `console.log/info/warn` заглушены, остаются
  `console.error` и строки `[LOGIN]` / `[REFRESH TOKEN]`.
- `docker logs nginx-proxy` — журнал внешнего nginx (хостовый `/var/log/nginx/` пуст).

## Откат

- **Код:** образы тегируются только `latest`, а старые образы удаляет ночной `prune`. Откат —
  `git revert` и пуш, CI соберёт прежний код заново.
- **Схема/данные:** миграции только вперёд. Если проблема всплыла после коммита миграции — новая
  исправляющая миграция или (в крайнем случае) восстановление из `~/rollback/pg-pre-<файл>-*.dump`.

## Ловушки сервера

- **`nginx.conf` смонтирован в контейнер как отдельный файл.** Docker привязывает такой mount к
  inode. Замена файла через `mv` или `scp`, как делают редакторы, создаёт новый inode, и контейнер
  продолжает видеть **старое** содержимое. `nginx -t` и `nginx -s reload` при этом проходят без
  ошибок. Правьте файл на месте (`sed -i`, `cat >`) или после замены делайте
  `docker compose up -d --force-recreate nginx`. Проверяйте результат через
  `docker exec nginx-proxy cat /etc/nginx/nginx.conf`.
- Лимит памяти бэкенда — 200 МБ. Очень большие Excel-файлы и массовые операции упираются в него
  (контейнер перезапустится, `RestartCount` вырастет).
- Тот же лимит у Postgres. `max_connections=50` и `shared_buffers=64MB` подобраны под маленький VPS.
